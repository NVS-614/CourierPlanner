1. What this service does

CourierPlanner is a Node.js and Express shipping integration service. Its primary API accepts shipping-related requests, routes supported operations to carrier integrations, and returns normalized responses. Supporting code provides rating, tracking, address validation, shipment persistence, SAP-facing modules, EDI generation, document handling, and scheduled/background jobs.

The main web application starts at index.js. A typical API request follows:

HTTP request
  -> global origin/CORS and body parsing middleware
  -> mounted route
  -> controller
  -> carrier factory / carrier implementation or shared service
  -> optional database, document, or tracking work
  -> formatted HTTP response

Not every folder is an endpoint mounted by the main Express app. Some SAP, EDI, and job modules have their own handlers or startup logic; verify their invocation and deployment path before assuming they are reachable through index.js.

3. Runtime and HTTP application

Starting the service

  • Runtime: Node.js 20 as declared in package.json.
  • Entry point: index.js; local command: npm start.
  • Port: PORT environment variable, falling back to 5001.
  • Swagger UI: /api-docs.

Middleware and request handling

The entry point applies origin checks and CORS, and configures XML, JSON, and URL-encoded body parsing. XML supports SAP-facing integrations. JSON and URL-encoded bodies have a configured 50 MB limit; XML parsing is limited to 1 MB. A final Express error handler logs errors and returns a JSON error response.

The origin check allows the Pack Planner origin and localhost development origins. Requests without an Origin header are not rejected by that origin-check middleware; CORS behavior is separately configured. Review both controls before changing cross-origin behavior.

4. Request and carrier flow

  1. A route declares the HTTP method/path and request middleware, such as upload handling.
  2. A controller validates and interprets the request, then calls a factory or shared service.
  3. A carrier implementation performs the provider-specific operation.
  4. The controller may persist successful results, generate documents, or invoke related services.
  5. The route/controller returns the operation response.

For example, the shipment route accepts a shipment request and can accept an in-memory invoiceFile upload. The shipment controller coordinates validation, carrier dispatch, requested document generation, persistence of successful shipment results, and the response. Tracking selects a carrier and calls its tracking operation.

Carrier modules do not necessarily implement identical operations. Check a carrier's exports and the relevant factory before assuming support or adding an operation.

Carrier coverage

The carriers/ tree includes ABF, Averitt, Blue Dart, Canada Post, DHL/DHL GF, Estes, FedEx/FedEx Freight, ODFL, Pitt Ohio, Purolator, RL, Saia, SEFL, UPS, USPS, XPO, and Generic integrations. The shipping factory discovers carrier directories and selects implementations; rating uses a separate rate factory. Exact support, configuration, and behavior vary by carrier and operation.

5. Data and shared services

PostgreSQL

database/db.js configures PostgreSQL access through pg-promise using DATABASE_URL. database/dbsaveandupdate.js contains application-level lookups and persistence functions, including carrier/service/ credential and shipper-location lookups, plus shipment, tracking, rates, transactions, and invoice-related operations.

Before changing persistence, trace the caller and inspect the SQL and expected database schema. This guide does not prescribe database table definitions or claim a local database is available.

Shared integration helpers

Reuse/, generic/, lib/, and utils/ contain shared API/token/transport helpers, FTP/SFTP support, response formatting, logging and error helpers, and the external document-engine client. Reuse established helpers when extending carrier behavior.

6. SAP, EDI, documents, and tracking

  • SAP: SAPSHIP/, SAPRATE/, SAPTRACK/, and SAPINVOICE/ contain SAP-facing shipment, rate, tracking, and invoice-event code.
  • EDI: edi/ contains X12 handling; edi/edi.js includes a handler that builds an 856 shipment notice.
  • Documents: ShippingDocuments/ has shipping document helpers; shipment processing can call an external document engine configured with DOC_ENGINE_URL.
  • Tracking: Route/controller code is under routes/ and controllers/; other tracking code is under TRACKING/ and jobs/.

Some modules define their own Express routers or handlers but are not mounted by the main index.js app. Their active invocation path may be a separate process or external integration; verify deployment configuration before treating them as main-app endpoints.

7. Background processing

jobs/ contains scheduled or batch processing code, including tracking and mail-related jobs. Procfile declares web and worker process types, but jobRunner.js currently only logs startup; its job imports are commented out. Confirm how jobs start in the target environment before relying on the worker declaration to run a schedule.

8. Configuration and secrets

.env.example lists example configuration keys and placeholders. Trace each setting to its consumer and set production values in the hosting environment. At minimum, documented integrations use settings such as DATABASE_URL and, where applicable, DOC_ENGINE_URL; carrier and SAP integrations may require additional credentials and endpoint settings.

Never copy real credentials from a local .env into source control, documentation, logs, or client-side code. Store production secrets in the deployment platform's secret/environment variable settings. The example file contains placeholders only.

Swagger Google sign-in

Google OAuth in middleware/swaggerGoogleAuth.js is specifically for Swagger, not shipping APIs. The requireAuth middleware is currently commented out in index.js, so /api-docs/ is publicly accessible. OAuth routes and session setup remain mounted. To enable the gate, configure the Google client ID/secret, callback URL, allowlisted Gmail addresses, and session secret from .env.example, then enable swaggerGoogleAuth.requireAuth and verify allowed and denied accounts.

9. Deployment and operations

  • Docker: dockerfile uses Node 20 Alpine, installs Chromium for Puppeteer, and starts index.js.
  • Cloud Foundry-style deployment: manifest.yml contains app/deployment metadata.
  • Process declarations: Procfile declares web and worker process types.
  • Port: The web process reads PORT, defaulting to 5001.
  • External dependencies: Database, carrier services, and optional document-engine integrations need configured credentials and network access.

For a release, verify that the configured process invokes the intended web and worker entry points. A declaration in a deployment file does not prove that a particular job or module is running.

10. Development and verification

  1. Install dependencies with npm install when setting up a checkout.
  2. Configure required local environment values without committing secrets.
  3. Start the web service with npm start.
  4. Open /api-docs to inspect the API contract.
  5. Use examples under requests/ where applicable and inspect the matching route/controller/carrier code.
  6. Exercise carrier operations only with suitable test credentials and non-production endpoints when available.

The current package.json does not define a test script, and no automated project test suite was identified during this documentation pass. Run appropriate checks for code changes and consider adding focused tests for new or changed behavior.

11. Maintenance checklist

  • Update relevant route, controller, factory, and carrier code together.
  • Confirm carrier operation support rather than assuming uniform capabilities.
  • Preserve request/response shapes described by Swagger and existing callers.
  • Verify database effects and failure handling for persistence changes.
  • Check XML parsing and request-size assumptions for SAP/EDI changes.
  • Confirm new routers are mounted or invoked in their deployed process.
  • Keep credentials out of source control and logs.
  • Update this guide when architecture, process entry points, or deployment behavior changes.
